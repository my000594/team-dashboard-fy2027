- nav.jsを読み込まない完全に独立したページ。`NAV_ITEMS`にも載せていないため、部下向けダッシュボードのメニューには一切表示されない
- スマホのホーム画面に追加すると、ブラウザのアドレスバー無しでアプリのように起動する（`apple-mobile-web-app-capable`等のメタタグ＋data URIのmanifest/アイコンで対応。画像ファイルは追加していない）
- 中身はGitHub REST APIを直接ブラウザから呼び出し、対象のワークフローをworkflow_dispatchでトリガーするだけの単一ページ。バックエンドは持たない
- 認証は**GitHubのPersonal Access Token（PAT）をこのページ内で入力し、ブラウザのlocalStorageに保存する方式**。トークンはリポジトリのソースコード・git履歴には一切含まれない。ページ自体は誰でもURLを知っていれば開けるが、トークンを持っていない限り操作はできない。2つの機能（メンテナンス切替・Notion同期）は同じトークン・同じ設定パネルを共用する
- 想定するトークン：このリポジトリ（`my000594/team-dashboard-fy2027`）のみに絞ったfine-grained PATで、権限は「Actions: Read and write」のみ（Contents権限は付与しない）。漏洩してもコードの読み書き・削除はできず、ワークフローのトリガー・実行状況の閲覧のみ可能な設計
- **メンテナンス切替**：現在の状態（`data/maintenance.json`をfetchして判定）に応じて「メンテナンスを開始」／「メンテナンスを解除」のどちらかを表示する大きいボタン。タップ即実行ではなく、誤操作防止のため必ず確認画面（開始／解除どちらも）を挟んでから`.github/workflows/maintenance.yml`をdispatchし、`data/maintenance.json`が実際に切り替わるまで数秒間隔でポーリングして反映を確認する。詳細設定（開始時のメッセージ・復旧見込み）は折りたたみ式で、空欄なら前回の内容を維持する仕様と対応している
- **Notion同期**（2026-08-09追加、2026-08-11に確認画面を追加）：「今すぐNotion同期を実行」ボタンをタップすると確認オーバーレイ（`confirmSync()`。メンテナンス切替と同じ`#confirmOverlay`を共用）を挟み、OKを押して初めて`.github/workflows/sync-notion.yml`をdispatchする。部下への公開状態には影響しない操作だが、押してすぐ動く導線自体が誤操作の入口になるため、メンテナンス切替と足並みを揃えて確認画面を必須にした（以前は確認画面無しの即時実行だった）。「同期状況を再確認」ボタン（既に追跡中のdispatchがある場合の表示）は新規dispatchではなく状況確認のみのため、こちらは従来通り確認画面を挟まない。dispatch APIは実行したworkflow runのIDを返さないため、dispatch直前の時刻を記録しておき、その時刻以降に作られたworkflow_dispatch起点のrunのうち最も古いもの（＝concurrencyグループで同時実行が1つに制限されているため、ほぼ確実に自分がキューに入れたrun）を自分のrunとみなして追跡する（`findRunSince()`。15秒のクロックずれ許容つき）。runが`completed`になるまでGitHub Actions APIをポーリングし、`conclusion`が`success`か否かで結果メッセージを出し分ける（失敗時も、sync-notion.mjs側の`section()`ラッパーにより成功したデータベース分は反映済みである旨を案内）
- **同期の追跡状態はlocalStorage（`sync_app_pending`）に逐次保存し、ポーリングループの途中経過に依存しない**（2026-08-09追加）。スマホでこのアプリをバックグラウンドに回したり閉じたりするとJSの実行自体が止まり、その場でのポーリングが続行できないことがある（実際に「実行中なのにタイムアウトメッセージが出た」という報告があった）。そのため、アプリを開いた時（`init`）とタブが再度前面に表示された時（`visibilitychange`）の両方で`resumeSyncIfPending()`を呼び、保存済みの状態から確認を自動再開する。追跡がタイムアウトした場合も「送信は成功している」ことを前提としたメッセージ（GitHub Actionsタブを見に行かせる案内ではなく「アプリを開き直せば確認を再開する」という案内）を出し、pendingは消さずに残す。実行完了（`completed`）を確認できた時だけpendingをクリアする。dispatchから20分（`SYNC_STALE_MS`）経っても未解決のpendingは放棄扱いにして自動クリアする
- **ポーリングの待ち時間は検出90秒・完了確認10分とかなり余裕を持たせている**（2026-08-09調整）。sync-notion.ymlはconcurrencyグループで同時実行を1つに制限しているため、毎日6:00 JSTの自動実行や直前の手動実行と重なると新しいrunがキューで待たされる。加えてNotion API不調時は30秒間隔で最大3回リトライする（`.github/workflows/sync-notion.yml`参照）。これらが重なると数分かかることがあり、以前の待ち時間（検出60秒・完了確認2分）では実際には成功しているのに時間切れメッセージが先に出てしまっていたため延長した。完了確認中は「実行中...（約N分経過）」のように経過時間を表示し、待っている間も動いていることが分かるようにしている
- **「同期状況を再確認」ボタン**：追跡中のpendingが残っている間（`renderSyncButtonState()`が判定）、Notion同期ボタンは「今すぐNotion同期を実行」ではなく「同期状況を再確認」に切り替わり、タップすると`resumeSyncIfPending()`をその場で呼び出す。アプリを開き直さなくても手動で再確認できるようにするための導線
- **「前回の同期」の常時表示**：ライブの追跡状態（自分が今送信したdispatchの行方）に依存せず、GitHub Actions APIから直接「直近の完了済みrun」（毎日6:00 JSTの自動実行・他の人による手動実行も含む）を問い合わせて表示する（`refreshLastSyncStatus()`。アプリを開いた時・前面に戻した時に呼ぶ）。結果は`localStorage`（`sync_last_result`）にもキャッシュし、次回起動時はまずキャッシュを即表示してから裏で最新化する。GitHub Actionsのタブを開かなくても「前回ちゃんと成功したか」をこのアプリだけで確認できるようにするための機能
- メンテナンス切替とNotion同期はどちらも同じ`busy`フラグで排他制御し、一方の実行中はもう一方のボタンも無効化する（同時多重実行の防止）
- GitHub REST APIはトークン認証リクエストに対してCORSを許可しているため、ブラウザから直接`fetch`で呼び出せる
